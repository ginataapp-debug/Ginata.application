5. DATABASE, TENANT ACCESS, AND STORAGE
---------------------------------------
The backend has SQLAlchemy models, startup table creation, and additive
migrations. Its PostgreSQL migration enables RLS and revokes direct anon and
authenticated table grants on tables owned by the database connection. The API
uses the database connection and derives organization scope from the logged-in
Ginata host. Automated tenant-boundary tests pass.

Still verify in the Supabase dashboard that Render DATABASE_URL points to this
project, the migrations completed, expected tables and foreign keys exist, and
the RLS/grants are present. Do not manually add broad RLS policies without
testing how the API database role is affected. Test two distinct production
hosts and confirm neither can access the other's records.

Current storage behavior:
- Property/brand images use the ginata-media Supabase bucket when backend
  service-role storage credentials are configured; otherwise they fall back
  to Render local disk.
- Generated invoices, receipts, and other documents are written to backend
  local storage and downloaded through organization-scoped API routes.
- Private-bucket policies, persistent document storage, signed URLs, and
  cross-host storage access have not been verified. Render local disk is not a
  substitute for durable private object storage.

Before storing sensitive guest IDs, move document storage to a durable private
bucket, enforce host/property ownership in backend operations, use short-lived
signed downloads, and test cross-host denial. Restrict uploads to documented
file types and sizes.

6. AUTHENTICATION AND ACCOUNT WORKFLOW
--------------------------------------
Existing email/password signup, login, reset, logout, and Google PKCE flows are
preserved. API calls use the production HTTPS API URL, existing request timeout
handling, and session validation. A 401 now clears the Ginata session and sends
the app back to sign-in. The login screen places "Forgot password?" below the
password field. Password recovery requires SMTP_HOST and SMTP_FROM_EMAIL plus
secure transport (SMTP_STARTTLS or SMTP_USE_SSL) in the backend environment.
Without that configuration, recovery now returns HTTP 503 rather than claiming
that a code was sent. Provider delivery failures retain a generic response to
avoid revealing whether an email belongs to an account; verify the provider
configuration and test delivery to a real controlled mailbox.

Backend automated tests include tenant boundary checks; they do not prove live
production account workflows. After deploying, test registration, verification
if enabled, login, logout, reset email delivery and login with the new password,
session expiry, profile edits, property/booking/finance/document workflows,
and persistence after re-login with two separate accounts. Confirm no secrets
are returned in API errors.
